### The Constitution of the Architecture

---

## 1. Purpose

This document is the constitution of the Sakhari Ecom architecture. It exists to answer one question consistently, forever: *when two reasonable approaches are both technically possible, which one does this project take, and why?*

Every other document in `/architecture` — decomposition, cross-cutting rules, deployment strategy, quality attributes — answers a narrower question within a domain. This document answers the question underneath all of them. It is written once, referenced constantly, and changed rarely and deliberately.

This document is binding on:

- Every future document under `/architecture`, which must be consistent with the principles stated here or must justify a deviation through the ADR process.
- Every Software Design Document (SDD), which translates a decomposed unit's design into detail — detail that must not contradict a principle established here.
- Every line of implementation, whether written by a human or generated by an AI coding assistant. Convenience at the point of writing code is never grounds for violating a principle — see Section 4.12.
- Every AI coding assistant operating on this codebase across sessions with no memory of prior conversations. This document is a primary part of what replaces that memory — see Section 9.

This document does not describe *what* the system does (that is the Software Requirements Document, SRD) or *how the data model is designed* (that is the Database Design Document, DDD). It describes the engineering philosophy and non-negotiable rules that govern *how the product becomes a running system*, before a single module boundary or schema is finalized.

---

## 2. Vision

Sakhari Ecom is a quick-commerce platform handling real money, real inventory, and real delivery promises to customers in Saudi Arabia, built and operated by a single developer working with AI coding assistants rather than a team. The architecture exists to make that combination — real commercial stakes, minimal human bandwidth — survivable and, over time, boring.

The system this architecture aims to produce is one where:

- Financial and inventory state is always correct, even when that costs some raw performance.
- A solo developer, returning to any part of the system after months away, can trust what the code does without re-deriving it from scratch.
- An AI coding assistant, with no memory of previous sessions, can be handed a task and produce a change consistent with everything that came before it — because the constraints are written down, not held in someone's head.
- Growth in order volume, store count, or team size is met by extending the architecture, not rewriting it.
- Compliance with Saudi regulatory obligations (SAMA, PDPL) is a property of the architecture itself, not a checklist bolted on afterward.

This is not an architecture optimized to impress at scale the business does not yet have. It is optimized to be correct, explainable, and cheap to operate at launch scale, while deliberately not foreclosing the path to a larger scale later. See Section 6 for the tradeoffs this implies, and Section 13 for how that path is kept open.

## 3. Engineering Philosophy

Four convictions run underneath every principle in this document:

**Correctness is a prerequisite, not a feature.** A fast system that sometimes double-charges a customer or oversells a product is not a fast system with a bug — it is a broken system that happens to respond quickly. Correctness is established first; performance is then pursued within the bounds correctness allows.

**Boring technology is a competitive advantage at this scale.** Every additional language, datastore, framework, or architectural pattern is maintenance debt paid by one person. The right technology choice for Sakhari Ecom is usually the well-understood, well-documented, unglamorous one — because its failure modes are known, its documentation exists, and an AI assistant is more likely to generate correct code against it.

**Structure follows the business, not the org chart or the framework's defaults.** With no team to divide along technical layers (a "backend team," a "database team"), there is no organizational pressure pushing the architecture toward technical-layer decomposition. It is decomposed around what the business does instead, deliberately — see Section 4.4.

**Explicit beats implicit, always.** A rule enforced by convention, memory, or "the way we've always done it" is a rule that will eventually be broken by someone — or something — that never learned the convention. Every principle in this document is written down for exactly this reason: so that neither a returning developer nor a memoryless AI assistant has to infer it.

## 4. Core Architectural Principles

These are the non-negotiable rules of the system. Each is stated once, explained, and bounded by the conditions (if any) under which it may be deviated from — always through the ADR process (Section 12), never silently.

### 4.1 Business Correctness Over Raw Performance

> When correctness and performance are in tension, correctness wins by default.

**What it means:** Financial state, inventory state, and order state must always reflect what actually happened — even when guaranteeing that costs extra locking, extra writes, or lower throughput than a looser design would allow.

**Why it exists:** This platform moves real money (mada, cash-on-delivery, BNPL) and real inventory across real delivery promises. An architecture that trades correctness for speed produces double charges, oversold stock, or orphaned orders — failures that cost far more, in money and in a solo developer's time, than any latency they saved.

**Benefits:** Predictable system behavior; financial and inventory records that can be trusted without manual reconciliation; fewer production emergencies.

**Drawbacks:** Some operations are deliberately more conservative — and slower — than a "move fast" design would allow. Aggressive optimizations on correctness-critical paths must justify themselves explicitly rather than being the default.

**Exceptions:** Permitted only on paths with no financial, inventory, or lifecycle consequence — browsing, search relevance, non-authoritative display data — and only once the correctness-critical path they sit beside has already been proven correct.

### 4.2 PostgreSQL Is the Single Source of Truth

> Durable business state exists authoritatively in PostgreSQL, and nowhere else.

**What it means:** Orders, inventory, payments, accounts, and entity lifecycle state live in PostgreSQL (Amazon RDS). Every other store in the system is a derived, disposable view of that truth.

**Why it exists:** A system with two authoritative stores inevitably produces a moment where they disagree, and no principled way to know which one is right. A single source of truth removes that failure mode by construction, and matches the finalized platform decision already made at the requirements level.

**Benefits:** One place to reason about consistency; one place to back up and restore; a data model simple enough for a solo developer — and an AI assistant with no session memory — to hold in their head.

**Drawbacks:** Every durable write must pass through Postgres even where a faster alternative store exists, which bounds throughput below what a more distributed design could theoretically achieve.

**Exceptions:** None for durable business state. Data that is inherently ephemeral or fully reconstructable is not "business state" and is governed by Section 4.3 instead.

### 4.3 Redis Accelerates but Never Owns Business State

> Redis may cache and coordinate. It may never be the only place a business fact exists.

**What it means:** Redis is permitted to hold sessions, rate-limit counters, real-time coordination state, and caches of data whose authoritative copy lives in PostgreSQL. No fact that matters to the business is allowed to exist only in Redis.

**Why it exists:** Treating a cache as a database is one of the most common ways distributed systems quietly lose data — a restart, an eviction, or a flush erases something nobody thought to protect because "it was just in Redis."

**Benefits:** Redis can be flushed, resized, or restarted at any time with zero business-data risk; the boundary between "accelerator" and "record of truth" stays unambiguous.

**Drawbacks:** Some read paths pay the cost of a Postgres round-trip, or a cache-then-verify step, that a design treating Redis as authoritative could avoid.

**Exceptions:** None for anything whose disappearance would constitute a business loss. Where Redis-backed coordination (for example, a distributed lock) is momentarily critical to correctness, the state it produces must still be committed to PostgreSQL before it is considered true.

### 4.4 Architecture Follows Business Capabilities

> The system is decomposed around what the business does, not around technical layers.

**What it means:** Units of the system are organized around business capabilities — ordering, inventory, dispatch, payments, identity — rather than around technical concerns like "all controllers" or "all data-access code."

**Why it exists:** Capability-aligned boundaries change at the same pace the business changes, keeping the architecture synchronized with the SRD's business capabilities and the DDD's entity ownership model rather than drifting from them. It is also what allows database ownership and module ownership to stay aligned instead of being reinterpreted through a technical lens.

**Benefits:** A change to one business capability rarely ripples into unrelated ones; the system's structure reads like the business itself, lowering the cost of a human or an AI assistant re-orienting with no prior context.

**Drawbacks:** Capability boundaries are harder to draw correctly up front than technical layers are, and a wrong boundary is expensive to redraw later.

**Exceptions:** None as a default orientation. The *granularity* at which capabilities are split — one module vs. several, one deployable vs. many — is expected to evolve; see Section 13.

### 4.5 Modules Own Their Own Data

> Each module is the only code permitted to read or write its own tables.

**What it means:** A module aligned to a business capability exclusively owns access to its own persisted data. Every other part of the system reaches that data only through the owning module's defined interface, never directly.

**Why it exists:** This is what makes Section 4.4 enforceable rather than aspirational. A capability boundary that anything can bypass with a direct query is not a boundary — it is a suggestion. This principle is the direct countermeasure to the cross-module repository access anti-pattern (Section 10).

**Benefits:** A module can change its internal schema without a system-wide audit of every caller; responsibility for a piece of data's correctness has exactly one home.

**Drawbacks:** Cross-cutting needs — reporting, admin dashboards — take more deliberate design than a single ad hoc join across tables would.

**Exceptions:** Reporting and analytics may read from a replica or a purpose-built read model, provided that read model is explicitly designed and documented as such — never a live shortcut into another module's operational tables.

### 4.6 Services Own Business Logic

> Business rules live in one layer, in one place, regardless of how many clients call them.

**What it means:** Validation, calculation, and business decisions live in service-layer code — not in controllers, not as ad hoc database triggers, and never duplicated across client applications.

**Why it exists:** Four client applications (Customer Mobile, Customer Web, Worker App, Admin Dashboard) consume the same backend. If business logic existed in more than one place, the clients would inevitably drift into inconsistent behavior — something the platform's own requirements explicitly rule out for the customer-facing surfaces.

**Benefits:** One place to fix a rule, one place to test it, guaranteed behavioral consistency no matter which client initiated the action.

**Drawbacks:** Services must be designed to be called correctly by any consumer, without silently assuming the shape or context of a particular client.

**Exceptions:** Purely presentational logic — formatting, layout, client-specific UX behavior with no business consequence — belongs in the client, not the service.

### 4.7 Controllers Remain Thin

> A controller translates a request into a service call and a response. Nothing more.

**What it means:** Controllers and equivalent entry-point handlers contain no conditionals, calculations, or decisions that affect a business outcome. Their job is translation, not judgment.

**Why it exists:** A controller is bound to a single transport and a single route. Logic placed there is invisible to every other entry point — a background job, another client, a future API — and is the most direct path to the business-logic-in-controllers anti-pattern (Section 10).

**Benefits:** Business rules stay reusable and testable independent of any transport; controllers stay legible at a glance, which matters for fast orientation by a human or an AI assistant.

**Drawbacks:** Requires routing even small-feeling logic through a service call rather than inlining it "just this once."

**Exceptions:** Validation and parsing that concern only the transport — is this request well-formed — may live at the controller boundary. Whether an action is *permitted* is a business decision and belongs in the service layer.

### 4.8 Events Are Asynchronous

> When one part of the system needs to tell another that something happened, that notification is asynchronous.

**What it means:** Downstream reactions to a business event — notifying a customer, triggering dispatch, updating analytics — travel as events the originating action does not wait on, rather than as a chain of synchronous calls.

**Why it exists:** A single order placement fans out to multiple concerns that do not need to succeed before the customer receives a response. Making that fan-out synchronous makes the entire chain only as fast and as reliable as its weakest downstream link.

**Benefits:** The originating action stays fast and is insulated from slow or failing downstream consumers; new consumers of an event can be added without changing the producer.

**Drawbacks:** Introduces eventual consistency for whatever the event triggers, and requires deliberate failure and retry handling on the consumer side rather than assuming delivery.

**Exceptions:** Outcomes that must be true before the caller receives a response — an order existing, a payment being authorized — are not modeled as events. They are part of the synchronous, transactional operation itself; see Section 4.9.

### 4.9 Transactions Protect Business Integrity

> Writes that must succeed or fail together are executed inside a single database transaction — never as hopeful separate steps.

**What it means:** Any set of writes with an all-or-nothing business requirement (reserving inventory while placing an order, capturing payment while confirming an order) executes inside one transaction, with no window where only some of it has happened.

**Why it exists:** Partial writes are how inventory goes negative, how a customer is charged with no corresponding order, and how state becomes unrecoverable without manual intervention — expensive for any team, and unrecoverable-by-morning for a solo developer without an operations team.

**Benefits:** The system never has to represent, or explain, an impossible intermediate state; failure handling is a rollback, not an improvised cleanup.

**Drawbacks:** Transactions must stay short and focused or they become a throughput and lock-contention liability — which is part of why Section 4.8 pushes everything that isn't strictly atomic out of the transaction and into an event instead.

**Exceptions:** None for genuinely all-or-nothing business operations. Sequences that only *look* atomic but are actually independent, individually valid business steps (picking, then packing) should be modeled as their own transactions with explicit state transitions, not forced into one.

### 4.10 Every Important Action Is Auditable

> Actions with financial, inventory, or lifecycle consequence leave a durable, append-only record of who did what, and when.

**What it means:** Payment events, order state transitions, catalog and price changes, and administrative overrides are recorded as facts that happened — not inferred later from the current state of a mutable row.

**Why it exists:** Disputes ("I was never charged," "I never received this order"), regulatory expectations under SAMA and PDPL, and a solo developer's own ability to reconstruct what happened months after the fact all depend on evidence existing, rather than being reconstructed from memory or trust.

**Benefits:** Disputes and incidents are resolved from evidence, not recollection; regulatory obligations have a concrete mechanism satisfying them rather than a promise.

**Drawbacks:** Every audited action carries a real, if small, cost in write volume and storage, and the audit trail itself must be protected from modification or deletion.

**Exceptions:** Purely cosmetic, freely-reversible actions with no financial, inventory, or compliance consequence (a customer changing a display preference) require only ordinary application logging, not audit-grade recording. The dividing line is consequence, not "did something change."

### 4.11 APIs Are Versioned

> A breaking change to the API contract is introduced as a new version — never as a silent change to an existing one.

**What it means:** The backend API surface shared by all four client applications carries an explicit version, and any change that would break an existing caller happens under a new version, leaving the old one intact until it is deliberately retired.

**Why it exists:** Two mobile apps on app-store release cadences, a web app, and a worker app distributed to staff all depend on one shared backend. A breaking change with no version boundary can strand a client mid-release with no recovery path except an emergency hotfix.

**Benefits:** Backend and clients evolve on independent schedules; a problematic client release does not force a synchronized backend rollback.

**Drawbacks:** Supporting more than one live API version simultaneously carries a real maintenance cost, which must be bounded by an explicit deprecation policy rather than left open-ended.

**Exceptions:** Additive, backward-compatible changes — a new optional field, a new endpoint — do not require a new version. Versioning exists to protect against breaking changes, not to gate every change.

### 4.12 Architecture Takes Precedence Over Implementation Convenience

> When a shortcut conflicts with a principle in this document, the principle wins — even when the shortcut would ship faster today.

**What it means:** No principle in this document is optional at the point of writing code because it would be inconvenient to follow. A locally convenient exception — skipping the service layer once, reaching into another module's table once — is not a smaller version of the rule; it is a violation of it.

**Why it exists:** This principle protects every other one. Each anti-pattern in Section 10 begins as a shortcut someone — human or AI assistant — judged acceptable "just this once." Without this principle stated explicitly and treated as binding, every other principle in this document is aspirational rather than real.

**Benefits:** Architectural integrity compounds instead of eroding one convenience at a time; an AI assistant with no memory of why a shortcut was taken cannot accidentally normalize it into a recurring pattern.

**Drawbacks:** Genuinely slows down some individual changes in the short term in exchange for long-term maintainability. This is an accepted, deliberate tradeoff — see Section 6 — not an oversight.

**Exceptions:** Only through the ADR process (Section 12): a deliberate, recorded, and reversible decision to deviate. An unrecorded shortcut is never an exception — it is exactly the violation this principle exists to prevent.

## 5. Design Goals

In priority order, the architecture is designed to achieve:

1. **Correctness of financial, inventory, and lifecycle state** — the system never represents something false as true.
2. **Maintainability by a single developer** — any part of the system can be understood, safely changed, and debugged by one person, with AI assistance, without requiring undocumented tribal knowledge.
3. **Compliance and security by default** — SAMA and PDPL obligations, and basic security hygiene, are properties of the architecture, not add-on tasks performed before launch.
4. **Operational simplicity** — the system can be run, observed, and recovered by one person without a dedicated operations function.
5. **Cost discipline at launch scale** — infrastructure spend matches the business's actual current scale, not a hypothetical future one.
6. **Acceptable latency for the delivery promise** — the customer-facing experience stays fast enough to support a 10–20 minute delivery expectation, within the bounds set by Section 4.1.
7. **Evolvability without rewrite** — the architecture can absorb growth in order volume, store count, or team size by extension, not replacement. See Section 13.

## 6. Design Tradeoffs

Every architecture accepts costs in exchange for benefits. Stating them explicitly prevents them from being silently relitigated later by someone who assumes they were accidental.

- **Consistency over throughput** on every path that touches money, inventory, or order lifecycle. Some throughput ceiling is accepted in exchange for never producing an impossible state.
- **A modular monolith over microservices at this scale.** Distributed-systems complexity (network partitions, distributed transactions, cross-service deployment coordination) is a cost this project does not need to pay yet, and should not pay speculatively — see Section 13 for how this can change.
- **Boring, proven technology over novel technology**, even where a newer option might offer a theoretical edge — because a well-understood failure mode is a solvable problem, and an obscure one is a solo developer's emergency.
- **Short-term development velocity is sacrificed for long-term auditability and correctness** — for example, the transaction and audit-trail requirements of Sections 4.9 and 4.10 take longer to build than skipping them would, deliberately.
- **Vertical scaling and simple caching are preferred before horizontal scaling or distributed architecture** — added complexity is deferred until load actually demands it, not provisioned in anticipation of load that may never arrive.
- **Synchronous simplicity is preferred over eventual-consistency complexity wherever correctness is at stake**, even though asynchronous design is used aggressively elsewhere (Section 4.8) — the two are not in tension because they apply to different classes of operation.

## 7. Architectural Constraints

These constraints are not choices this architecture makes — they are conditions imposed on it from outside, by the SRD or by circumstance, that every principle and every future document must operate within.

- **One developer.** Every additional service, language, framework, or operational surface is maintenance debt paid by a single person. This constraint is the primary justification for Section 6's tradeoffs.
- **AI-assisted development, without persistent memory across sessions.** Architecture must be legible enough, and documented explicitly enough, that an AI coding assistant can act correctly on a task without having participated in the decisions that led here.
- **Saudi Arabia only at launch.** Data residency, SAMA and PDPL compliance, and mada payment support are not optional regional considerations — they are baseline requirements the architecture must satisfy from day one, not retrofit later.
- **Cash-on-delivery is a significant share of orders.** The architecture cannot assume payment is always pre-authorized or guaranteed before fulfillment begins; order and payment state must model this honestly rather than as an edge case.
- **Arabic is a first-class requirement, not a deferred one.** This is a product/localization constraint with architectural weight wherever the system generates or stores user-facing text.
- **Launch scale is low thousands of orders per day, across a handful of cities.** The architecture is sized for this reality, not for a hypothetical scale the business has not yet reached — consistent with the cost-discipline goal in Section 5.
- **Four client applications, one backend.** The Customer Mobile App, Customer Web App, Worker App, and Admin Dashboard all depend on the same backend API and business logic, with no divergent logic between customer-facing clients — this constraint directly underpins Sections 4.6 and 4.11.

## 8. Coding Philosophy

This section governs how code is written in service of the architecture, without prescribing implementation detail:

- **Readability over cleverness.** Code is read far more often than it is written, especially by a returning developer or an AI assistant with no memory of writing it. A clever solution that requires re-derivation is a worse solution than an obvious one, even if the obvious one is a few lines longer.
- **Naming reflects the product's business language.** Identifiers use the vocabulary established by the SRD and the entity names established by the DDD, not ad hoc technical synonyms — so that code, requirements, database design, and conversation about the system stay in the same vocabulary.
- **No speculative abstraction.** Structure is built for the requirement in front of it, not for a hypothetical future requirement. An abstraction earns its existence by serving two or more real, current needs — not by anticipating a third that may never arrive.
- **Error handling exists at boundaries, not everywhere.** Input from outside the system (client requests, external provider responses) is validated and defended against at the boundary; internal code trusts the guarantees already established by that boundary rather than re-checking them defensively at every layer.
- **Tests protect business rules, not implementation shape.** A test exists to prove a business rule holds (an order cannot be placed against insufficient stock), not to lock in the internal structure of the code that happens to enforce it today.
- **Consistency is enforced by tooling, not memory.** Formatting, linting, and structural conventions are automated wherever possible, so that consistency does not depend on every contributor — human or AI — independently remembering the house style.

## 9. AI Development Philosophy

Sakhari Ecom is built with AI coding assistants as a primary means of implementation. This section states the terms of that participation.

- **Architecture decisions are owned by the architecture, not inferred by the assistant in the moment.** An AI assistant implements within the boundaries this document and its subordinate documents establish; it does not independently decide a new service boundary, a new datastore, or a new cross-cutting pattern belongs in the system.
- **Documentation is the substitute for memory.** An AI assistant does not retain context between sessions. The `/architecture` folder exists specifically so that a memoryless assistant, given a task cold, can still act consistently with every decision made before it. Treating this documentation as optional context defeats its purpose.
- **AI-generated code is held to the same bar as human-written code.** "An AI assistant wrote it quickly" is never a justification for a principle violation reaching the codebase. Section 4.12 applies identically regardless of who, or what, wrote the shortcut.
- **When architecture is ambiguous, the assistant asks or proposes — it does not silently improvise.** A gap in the documented architecture is not license to invent a permanent pattern unilaterally; it is a signal to surface the gap, propose an approach, and — where the decision is significant — record it as an ADR rather than letting it become precedent by accident.
- **The assistant does not amend this document, or restructure `/architecture`, without explicit human direction.** This document is a governance artifact, not implementation output. An assistant that identifies a real conflict between this document and reality proposes a change; it does not resolve the conflict by quietly rewriting the constitution.
- **Consistency across sessions is a measure of success.** An architecture that a memoryless assistant can act on correctly, repeatedly, without re-explanation, is doing its job. Where an assistant repeatedly gets something wrong, that is a signal the documentation is unclear or incomplete — not that the assistant needs to be reminded verbally each time.

## 10. Anti-Patterns

These are not style preferences — each is the direct, named failure mode a principle in Section 4 exists to prevent. Their presence in a change is grounds for rejecting it outright, not a stylistic nitpick.

**Cross-module repository access.** Code in one module directly querying or writing another module's tables, bypassing its owning interface. Violates Section 4.5. Cost when it happens: a schema change in one module silently breaks another, with no compiler or contract to catch it. No standing exception — the fix is a proper interface or an explicit, documented read model.

**Business logic inside controllers.** A decision that affects a business outcome living in a route handler instead of a service. Violates Sections 4.6 and 4.7. Cost when it happens: the rule is invisible to every other caller of that business capability (another client, a background job) and silently diverges the moment a second entry point is added.

**Shared mutable state.** State held in memory (or elsewhere) and mutated by more than one part of the system outside of a transaction or a well-defined ownership boundary. Cost when it happens: behavior becomes dependent on execution order and timing — the hardest class of bug to reproduce and the easiest to reintroduce by accident.

**Circular dependencies.** Two modules or services each depending on the other, directly or transitively. Violates Section 4.4's premise that capabilities are independently comprehensible units. Cost when it happens: neither module can be understood, tested, deployed, or changed in isolation, defeating the purpose of decomposition entirely.

**Direct database access between modules.** A variant of cross-module repository access where a consumer connects to another module's data at the database level (a raw query, a shared connection used to reach outside one's own tables) rather than even attempting to go through code. Cost when it happens: even a rewritten, well-encapsulated module can still be silently broken by a caller nobody can see from its own codebase.

**Silent failure of consequential actions.** An operation with financial, inventory, or lifecycle consequence that fails without producing an auditable record or a surfaced error. Violates Section 4.10. Cost when it happens: the system's records no longer match reality, and nobody is aware until a customer or a reconciliation catches it.

**Premature optimization ahead of proven correctness.** Optimizing a correctness-critical path before its correctness is established and tested. Violates the ordering in Section 4.1. Cost when it happens: performance work has to be redone once the correctness bugs it introduced or obscured are found.

## 11. Engineering Principles

Broader practices that support the core architectural principles without rising to their level of centrality:

- **Idempotency for anything that may be retried.** Payment operations, event handlers, and any action a client or queue might resend must produce the same end state whether executed once or several times — a direct consequence of taking cash-on-delivery, mobile networks, and asynchronous events (Section 4.8) seriously.
- **Fail fast at boundaries, trust internally.** Validate rigorously where the system meets the outside world; do not re-validate the same guarantee repeatedly once inside a trusted boundary.
- **Backward compatibility by default.** A change should not require every consumer to change in lockstep unless the change is genuinely breaking — and a genuinely breaking change follows Section 4.11's versioning discipline.
- **Security is a default state, not an added feature.** Authentication, authorization, and data protection are present from a capability's first version, not layered on before launch.
- **Observability is not optional.** A production issue that cannot be diagnosed from logs, metrics, or the audit trail (Section 4.10) is a design gap, not bad luck — especially for a solo developer with no second pair of eyes to compensate.
- **Small, reviewable changes.** A change sized to be understood in one sitting is safer for a solo developer to reason about and safer for an AI assistant to generate correctly than a large, multi-concern change.
- **Documentation is part of "done."** A capability whose behavior lives only in code, with no corresponding update to the relevant architecture or design document, is unfinished work — see Section 9's point on documentation as the substitute for memory.

## 12. Decision-Making Guidelines

When a new architectural question arises that this document does not explicitly answer, or when two principles appear to pull in different directions, resolve it in this order:

1. **Data integrity and correctness** (Sections 4.1, 4.2, 4.9) — never compromised for anything below this line.
2. **Security and regulatory compliance** (Section 7's SAMA/PDPL constraints, Section 4.10's auditability) — never compromised for anything below this line.
3. **Long-term maintainability by a solo developer** (Sections 3, 5, 6) — weighed against, but generally prioritized over, short-term convenience or velocity.
4. **Operational and cost simplicity** (Sections 5, 6) — preferred over theoretical scalability the business does not yet need.
5. **Performance and developer convenience** — the last tiebreaker, not the first.

Two further tools apply to any decision, large or small:

- **One-way doors get more scrutiny than two-way doors.** A decision that is cheap to reverse (a naming convention, an internal module split) can be made quickly and adjusted later. A decision that is expensive or impossible to reverse (a choice of system-of-record datastore, a public API contract, a data-residency-affecting infrastructure choice) warrants slower, more deliberate consideration and, where it deviates from or extends this document, an ADR.
- **When genuinely uncertain, default to the more conservative and more reversible option.** It is cheaper to relax a conservative decision later, once evidence justifies it, than to unwind a permissive one after it has caused damage.

Any decision that deviates from a principle in Section 4, or establishes a new pattern of similar weight, is recorded as an ADR under `decisions/` — see that folder's `README.md` for the process. A decision made without that record does not carry the authority of this document, no matter how reasonable it seemed at the time.

## 13. Future Evolution Philosophy

This document is deliberately hard to change, and the system it governs is deliberately not.

**The architecture earns its complexity.** Nothing described here — a new service extracted from the monolith, a new datastore, a distributed pattern — is adopted speculatively. It is adopted when evidence (real load, a real operational limitation, a real team-size change) demonstrates the current approach has actually stopped working, not when it seems like it might eventually.

**The modular monolith is a starting point, not a ceiling.** Because Section 4.4 and 4.5 already require the system to be decomposed around business capabilities with enforced data ownership, any capability can be extracted into an independently deployed service later without a redesign — the boundary already exists; only its deployment changes. This is why those two principles are classified as stable in the wider documentation set: they are what keeps this door open.

**Principles are stable; their application is not.** The twelve principles in Section 4 are not expected to change for the life of this project. How they are applied — the granularity of modules, the specific technologies accelerating Redis's role, the shape of the event system — is expected to evolve as the business does, within the bounds those principles set.

**This document changes only through explicit amendment.** A change to this constitution is itself a decision of the highest order and must be:

1. Proposed with the same rigor as a significant ADR — what's changing, why, and what it costs.
2. Recorded as a new version of this document, with the prior version preserved in version control history, never edited in place to obscure what changed.
3. Reflected immediately in the `architecture/README.md` index and `architecture/CHANGELOG.md`, so no document set ever silently disagrees with its own constitution.

**Deprecation is explicit.** If evolution ever renders part of this document obsolete, that part is marked superseded, with a reference to what replaced it and why — following the same immutability discipline the ADR process already applies to individual decisions. Nothing in this document simply stops being true without a record of when and why.
