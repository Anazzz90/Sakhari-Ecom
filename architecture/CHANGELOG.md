# Architecture Documentation Changelog

Tracks changes to the `/architecture` documentation system itself — structural changes (new documents, renamed sections, changed conventions) — not the content decisions recorded inside individual documents or ADRs. Content-level history for a specific document lives in that document's own edit history (git blame) and in the ADRs that justified the change.

Newest entry first. Each entry: date, what changed, why.

## 2026-07-26 — Coding Standards authored (eighth of the new documentation phase); new 07-coding-standards/ folder
Authored `07-coding-standards/coding-standards.md`, a genuinely new document with no prior skeleton, in a new `07-coding-standards/` folder — the structure previously proposed and approved for this and the upcoming AI Development Rules document. Expands `00-Architecture-Principles.md` Section 8 (Coding Philosophy) into concrete, checkable practice: repository and module structure (module directories mirroring `module-catalog.md` exactly, with data-access code unreachable from outside its own module — the structural expression of ADR-0009), naming conventions (code vocabulary matches documentation vocabulary exactly), logging, validation, and error-handling standards, testing philosophy (tests protect business rules and are weighted toward correctness-critical and idempotency-sensitive paths), documentation standards, a code review checklist, and a separate architecture-compliance checklist. Deliberately does not mandate a specific test framework, linter, repository topology (monorepo vs. polyrepo), or coverage threshold — none of these are decided in any prior document, and each is named explicitly in its own Open Decisions section rather than invented. `README.md` updated: new folder in the tree and purpose table, a tenth step added to Order of Authorship, and a stability-table entry.

## 2026-07-26 — Performance & Scalability authored (seventh of the new documentation phase)
Authored `04-cross-cutting/reliability-and-performance.md` in place of its prior skeleton, retitled to cover both its original scope (availability targets, latency budgets, failure-handling strategy) and the requested Performance/Scalability content: performance philosophy, caching strategy (Redis vs. CDN, why two layers), search strategy (Search module's index as a performance mechanism, not just a feature), read/write optimization (Analytics and Search removing read load architecturally before read replicas are considered), queue usage (event dispatch and background jobs both built on infrastructure already in the stack, no new queue technology introduced), horizontal scaling (stateless JWT-based requests and shared Redis coordination as the properties that make it straightforward when needed), database scaling (read replicas for read load, partitioning for append-only table growth — two distinct mechanisms for two distinct problems), future microservice extraction (confirming Order/Inventory as the named candidates from `module-catalog.md` without repeating the reasoning), and capacity planning principles (size for the business that exists, monitor before scaling, prefer the cheapest sufficient lever). Carries its own Open Decisions section (exact SLA numbers, specific scaling trigger thresholds, partitioning specifics — all explicitly deferred elsewhere already). `README.md` updated accordingly.

## 2026-07-26 — Deployment Architecture authored (sixth of the new documentation phase)
Authored both `05-deployment/environment-strategy.md` and `05-deployment/infrastructure-and-release.md` in place of their prior skeletons, together covering the requested Deployment Architecture scope split logically across the two existing files: `environment-strategy.md` covers Production Environment (a three-environment model — Development/Staging/Production — deliberately not larger, given the one-developer constraint), what varies per environment (external-integration sandbox-vs-live mode being the load-bearing variation), and the promotion path; `infrastructure-and-release.md` covers Infrastructure Components, Networking, Storage, Cache, Logging, Monitoring, Backup, Disaster Recovery, CI/CD, and a Scaling Strategy overview (deliberately kept light, deferring to `11-Performance-Scalability.md`).

Per this task's own instruction, cloud-provider and infrastructure details were kept abstract everywhere no prior document had already decided them (specific compute service, network topology, exact backup retention/RPO/RTO, specific CI/CD tool) — each named explicitly in Open Decisions rather than invented. This also resolves `data-architecture.md` Section 14's explicitly deferred RPO/RTO framing: the mechanism (managed automated backups, point-in-time recovery, single-region-with-disciplined-backups) is now established, though specific numeric targets remain open. `README.md` updated accordingly.

## 2026-07-26 — Event Architecture authored (fifth of the new documentation phase)
Authored `04-cross-cutting/integration-and-messaging.md` in place of its prior skeleton, retitled Event Architecture and covering the asynchronous/event half of that file's original scope in full: domain events, event naming, publisher/consumer rules, background processing (mapping all seven DDD-named background jobs to their relationship with the event system), the complete notification flow, retry strategy (publish-failure vs. consumption-failure, handled differently), idempotency as the baseline assumption for every consumer, event versioning (mirroring ADR-0017's API-versioning discipline), and the future event-bus strategy for eventual module extraction. Finally resolves the Audit invocation-mechanism question carried forward from `module-communication.md` and `data-architecture.md`: Audit consumes existing domain events where one already exists for other reasons, and receives a direct synchronous call only where no natural event exists (e.g., viewing sensitive data). The original skeleton's other two sections (synchronous API conventions, external-integration retry/circuit-breaking patterns) and its integration-inventory section are explicitly not covered here and are named in this document's own Open Decisions rather than silently dropped. `README.md` updated accordingly.

## 2026-07-26 — Security Architecture authored (fourth of the new documentation phase)
Authored `04-cross-cutting/security-and-compliance.md` in place of its prior skeleton, retitled Security Architecture while retaining its original SAMA/PDPL compliance-mapping scope. Covers identity (the Auth/User split), OTP-based authentication (and its reuse for rider delivery-confirmation), JWT's architectural role, refresh-token rotation with reuse detection, RBAC and the fine-grained permission model (ADR-0012), API security (validation at the boundary, Redis-backed rate limiting, symmetric trust treatment of external responses), audit's security framing (distinct from but complementary to `data-architecture.md`'s data-mechanics treatment of the same module), secrets handling (JWT signing keys as the highest-blast-radius secret; per-module external credential isolation), and a compliance-obligation-to-control mapping table. Carries its own Open Decisions section (exact token lifetimes, the full permission list, Support-module permission scope pending `module-catalog.md`'s Open Decision 1). `README.md` updated accordingly.

## 2026-07-26 — Data Architecture authored (third of the new documentation phase)
Authored `04-cross-cutting/data-architecture.md` in place of its prior skeleton (rather than creating a new file), since its existing scope already matched what was requested. Covers PostgreSQL and Redis philosophy, data ownership, transactions, the inventory model (Inventory Item / Reservation / Ledger as three distinct entities), the reservation lifecycle (requested → reserved → consumed/released-or-expired), the inventory ledger's role as history explaining current state, soft-delete vs. immutable vs. state-driven entity treatment, and the practical (not re-argued) consequences of the ULID, UTC, and integer-halala-money ADRs. Concurrency strategy (locking, optimistic validation, idempotency, named race conditions) and a data-level recovery strategy (compensating actions, reconciliation jobs, the ledger/audit trail itself) are both grounded directly in DDD Sections 9–15, with infrastructure-level backup/DR explicitly scoped out to the future `10-Deployment-Architecture.md`. Partially resolves `module-communication.md`'s open question on Audit's invocation mechanism (confirmed as a push model per DDD Section 12.1; the exact call-vs-event mechanism remains open for `09-Event-Architecture.md`). Carries its own Open Decisions section (deadlock-avoidance ordering, Audit's exact push mechanism, archival timing, retention-window specifics). `README.md` updated accordingly.

## 2026-07-26 — Module Communication authored (second of the new documentation phase)
Authored `03-decomposition/module-communication.md`: the four allowed forms of communication (client-to-backend REST, in-process module interface calls, domain events, module-to-external-system calls) and their forbidden counterparts; the full inter-module dependency graph as five layers (Foundation, Reference, Commerce, Transaction Orchestration, Fulfillment, Consumer tier), built from `module-catalog.md`'s per-module dependency fields; transaction-boundary rules establishing that no transaction ever spans two modules (cross-module consistency is achieved by orchestration with explicit compensation, not distributed transactions); and circular-dependency prevention, including the event mechanism's role as the designed escape valve for relationships that would otherwise require an upward dependency.

This resolves two points `module-catalog.md` had left open: (1) Payment initiation is a direct synchronous call from Order, not event-triggered — `module-catalog.md`'s Payment entry was given a small corrective edit to match; (2) the tension between ADR-0010's "single transaction" wording and the DDD's two-transaction model (Section 9.1/9.2) is resolved in favor of the DDD's model plus an orchestration-with-compensation pattern, with a note that ADR-0010's wording should eventually be tightened by a clarifying ADR. `README.md`'s folder tree and purpose table were updated accordingly.

## 2026-07-26 — Module Catalog authored (first of a new documentation phase)
Authored `03-decomposition/module-catalog.md`, the first of a planned nine-document phase (Module Catalog, Module Communication, Data Architecture, Security Architecture, Event Architecture, Deployment Architecture, Performance/Scalability, Coding Standards, AI Development Rules) requested against a fifteen-module backend list (Auth, User, Store, Catalog, Search, Inventory, Cart, Order, Payment, Promotion, Delivery, Notification, Analytics, Audit, Settings). Per the requester's own instruction, new documents are being slotted into the existing nested folder structure rather than flattened to a new root-level numbering scheme, to preserve the current structure and its cross-references.

The fifteen-module list does not fully match the DDD's nineteen-module-owner breakdown or the ADS's nine-capability grouping — most notably, the DDD's Support, Refund, Picking, Workforce, and Pricing modules have no direct counterpart, and Search is entirely new. Rather than resolve these silently, `module-catalog.md` documents seven specific reconciliation points in its own Open Decisions section (Section 3) and applies working assumptions consistently throughout, flagged as unconfirmed. `capability-boundary-map.md`, `service-decomposition.md`, and `data-ownership-map.md` were each given a short note pointing to `module-catalog.md` as the new primary per-module source of truth, to be summarized rather than duplicated when those three are eventually authored. `README.md`'s folder tree and purpose table were updated accordingly.

## 2026-07-26 — Technology Decisions authored
Authored `04-cross-cutting/technology-decisions.md`, documenting every technology in current use — React Native, Next.js, React/Vite (Admin Dashboard), NestJS, PostgreSQL, Redis, S3, JWT, OTP, Cloud Infrastructure (AWS), and CDN — each with Purpose, Why Chosen, Alternatives Considered, Benefits, Drawbacks, and Future Replacement Strategy. This expands the ADS's Section 9 (Technology Decisions) into full detail and is the connective layer between that category-level summary and the individual ADRs: it cross-references rather than duplicates the six technologies that already have a dedicated ADR (PostgreSQL — 0003, Redis — 0004, React Native — 0006, Next.js — 0007, React/Vite — 0008, Object Storage — 0016), and names five technologies with no dedicated ADR yet (NestJS, JWT, OTP, Cloud Infrastructure provider specifics, CDN) as backfill candidates, consistent with the pattern used for ADRs 0002–0017. `README.md`'s folder tree, purpose table, and Current Status were updated accordingly.

## 2026-07-26 — ADR-0018 corrected: ULIDs restored (ADR-0019)
The project owner confirmed that ULID, not UUID, was always the intended primary-key decision — the DDD's UUID text (which ADR-0018 had reasoned from) was itself the error. Corrected `DDD_Sakhari_Ecom_v1.0.md` Sections 1.2, 2.3, and 3.1 back to ULID, with rationale text updated to treat lexicographic sortability as a benefit rather than a leak. Authored `decisions/0019-restore-ulid-primary-keys.md` to supersede ADR-0018 rather than silently editing it, preserving the full decision history (0013 ULID → 0018 UUID, based on a draft DDD error → 0019 ULID, based on the corrected DDD) per the ADR immutability rule in `decisions/README.md`. ADR-0018's Status line was updated to `Superseded by 0019`; the index and this changelog reflect the current effective decision (ADR-0019, ULIDs).

## 2026-07-26 — System Context authored; DDD cross-checked; ADR-0013 superseded
Authored `02-context/system-context.md` in full, expanding the ADS's Section 6 into a complete system-context model across four zones — Customer Platform, Operations Platform, Backend, Infrastructure — each with Responsibilities, Boundaries, Trust Boundaries, External Integrations, and Internal Integrations, plus a consolidated "Diagram-Ready Model" (Nodes/Edges tables) so a future C4 Level 1/2 diagram can be generated directly from it without re-deriving the model. "Operations Platform" is introduced as this document's collective name for the Worker App + Admin/Ops Dashboard, mirroring the ADS's existing "Customer Platform" term.

This is the first document authored after `DDD_Sakhari_Ecom_v1.0.md` became available. Cross-checking against it surfaced two real findings, both incorporated: (1) the DDD confirms two external systems not previously named anywhere in the architecture set — a Push Notification Service and a Geocoding/Maps Provider (DDD Section 5.3) — now added to `system-context.md` with explicit notes on what's confirmed vs. still open (Worker App push, and whether geocoding is client-embedded or backend-mediated); (2) the DDD's Section 1.2/2.3/3.1 specifies UUID primary keys, directly conflicting with ADR-0013's prior choice of ULIDs (authored before the DDD existed). Rather than leave that contradiction standing, `decisions/0018-uuid-primary-keys.md` was authored to supersede ADR-0013 per the ADR lifecycle rules; `0013`'s Status line was updated to `Superseded by 0018` (its Decision/Rationale content left untouched, consistent with ADR immutability), and both `decisions/README.md`'s index and this changelog reflect the change.

## 2026-07-24 — First 16 substantive ADRs backfilled (0002–0017)
